# 文件头与落点：三组写法对照

## 一、五要素的合格写法

下面是一份虚构脚本的完整文件头，逐行都有用：

```
GENERATED-BY: session-0000 (agent, 2027-03-04 09:12 +08:00)
LAST-EDIT: session-0000 (agent, 2027-03-04 11:40 +08:00)（第 2 版：把「按行切」改成「按块切」，因为行内分隔符会跨行）
PURPOSE: 把上游三份 CSV 合成一张宽表，供下游特征计算读取
ORIGIN: pipeline/legacy/merge_v0.py（2027-02-11 旧版，保留在原处）
CUMULATIVE-DELTA: 首版按行切；本版按块切并加了分隔符跨行检测；两次改动合并成本句，不记流水账。
```

四行分别回答：**谁生成 · 谁最后改的以及改了什么 · 这文件干什么 · 相对上一版差在哪**。

## 二、三种常见写错

**① 只写日期不写时区，或只写到天。**
`LAST-EDIT: 2027-03-04` —— 同一天改过三次就分不清先后。规则要求**写到分钟 + 时区**，因为这个项目的坑集中在同一天内的多次动作。

**② `CUMULATIVE-DELTA` 记成流水账。**
```
❌ 第 1 版改了 A；第 2 版改了 B；第 3 版改回 A
✅ 最终形态：按块切 + 分隔符跨行检测（中间的来回已合并）
```
判据：同一处改过三次也只能出现一次，写**最终形态**。

**③ 标签都在，内容没更新。**
`Select-String 'GENERATED-BY:|LAST-EDIT:|PURPOSE:'` 全绿，但它只证明**标签存在**。
要另看：`CUMULATIVE-DELTA` 里有没有**本轮的日期与一句话**。

## 三、落点：一条信息该放哪

| 这条信息 | 放哪 | 判据 |
|---|---|---|
| 「某次运行通过率 62%」 | `runs/<编号>/RESULT.md` | 会漂 ⇒ 台账 |
| 「清洗步骤必须幂等」 | `pipeline/AGENTS.md` | 改行为 ⇒ 规则 |
| 「上游数据源每季度换一次格式」 | `docs/SOURCES.md` | 外部事实 ⇒ 资料线 |
| 「我猜到它可能是缓存问题」 | `runs/<编号>/NOTES.md` 并标【推断】 | 未验证 ⇒ 细节 + 标签 |

⚠️ 最常见的错：把第一行写进入口文件。它当时是对的，三个月后它还是那样写着，而已经不对了 —— **而且不报错**。
