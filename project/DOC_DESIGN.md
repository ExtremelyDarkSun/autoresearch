# 文档与台账设计规范

## 这份文档是什么

**一堆文档之间的分工规则**：谁是大纲、谁是细节、谁是唯一出处、旧内容往哪滚。
读者：准备新开一份文档、或判断「这东西该放哪一层」的人。时机：落笔之前，不是写完之后。

## 里面放什么

- 三层结构（大纲 / 细节 / 机器账）与判定它们的三问
- 大纲层那五格：一格只能有一份，各格管什么
- 细节层怎么跟产生它的那次动作走
- 跨专题资产、挂起的事、归档件这三类特殊东西的唯一落点
- 一条口诀：要不要新开一份文件

## 不放什么（放去哪）

| 不写 | 写到哪去 |
|---|---|
| 单份文档内部怎么切、上限多少、怎么滚冷件 | 维护入口与其正文 |
| 某个专题的假设、读数与判词 | 该专题自己的台账 |
| 当前有哪些活跃台账 | 维护清单 |
| 会漂的量：进度、版本、机器、费用 | 各自正文 |

## 一条判据：这条信息该放哪

问一句就够：**它只对某一轮动作有意义吗？** 是 ⇒ 细节层，跟那次动作走。否 ⇒ 再看它是不是「随时可由程序重算」⇒ 是就进机器账，否则进大纲层。

## 1. 三层结构：先判「这份东西属于哪一层」

任何一份新东西，落笔前先问：**它是大纲、细节，还是机器账？**

| 层 | 回答什么问题 | 读者 | 典型形态 | 有效期 |
|---|---|---|---|---|
| **大纲** | 要什么、现在到哪、下一步验什么 | 人（一页读完） | 专题主文档 · 现状页 | 整个专题 |
| **细节** | 这一轮具体怎么设计、怎么跑 | AI（每轮开工） | 计划文件 · 单轮分析 | 一轮实验 |
| **机器账** | 这一条是谁、什么时候、带什么机器件产生的 | 机器（闸与工具读） | 台账、登记库、回执 | 永久，只追加 |

**三问判据**（顺序问，先命中先用）：

1. **删掉它，人还能回答「现在到哪、下一步做什么」吗？** 能 ⇒ 它不是大纲，往下走。
2. **它只对某一轮动作有意义吗？** 是 ⇒ 细节层，跟那一轮走。
3. **它能由程序从别的文件重算出来吗？** 能 ⇒ 机器账，不手工维护。

⚠️ **最常见的错位**：把「细节」写成「大纲」—— 于是一个专题目录里出现十几份「某个时刻的分析」和「某一轮的供料」。**大纲层只回答三个问题，多出来的都是细节。**

## 2. 大纲层：五格台账，一格只能有一份

大纲层的五个格子是**彼此的唯一边界**：不许有第六格，也不许一格两份。

| 格 | 谁能改 | 什么时候改 |
|---|---|---|
| **目的与假设** | 负责人 | 每轮实验前后各一次 |
| **现状（给人和给 AI 各一份）** | 负责人供料、独立写手成文 | 起跑、阶段结果、停跑、被替代、结束 |
| **数据账** | 任何人只追加 | 每产生一个数就追加一行 |
| **待定与未决** | 负责人 | 有新问题时 |
| **流程状态** | 只有机器写 | 每跳 |

硬规则：**同一件事只在一格里写正文**，其它格只能指过去。两格都写正文，必定漂。

## 3. 细节层：跟着它产生的那次动作走

细节不放在大纲层，也不集中到一个「分析」目录。它跟着**产生它的那次动作**：一次实验一个子目录，一次审计一份报告。

**结论进大纲**：细节文件里**能改变判断的那一句**，要写进大纲层的对应格；细节文件本身只是留证。

⚠️ **不要把长分析塞进数据账**：那是「每个数一行」的账，塞长分析会把索引变成正文，两边都难读。

## 4. 跨专题资产：不放任何专题目录

一份东西如果**别的专题也要用**，它就不属于任何一个专题。放回上一层的公共位置，靠**登记进必读清单**获得可见性 —— 不靠它躺在谁的目录里被人偶然发现。

本模板里已经有一份跨专题资产：[机制清单](<AutoDL实验/实验分析/MECHANISMS.md>)（一条机制一行：改善哪个过程指标 · 适用与不适用 · 结论与证据）。专题里第一次出现的机制留正文给那一轮，只有在「下一个专题也要用」时才在这份清单里补一行指针。

搬走时**必须留指针**：原位置留一个三行存根，写明「已移到哪、为什么移、旧相对路径怎么跳」，否则历史文件里的相对引用会静默断掉。

## 5. 挂起的事：只有一个落点

等审批、等某一轮读数、等机器与额度的事，**一律登记到同一个等待簿** —— [`AutoDL实验/实验分析/WAITING.md`](<AutoDL实验/实验分析/WAITING.md>) —— 不再各自开一份「设计」。

**每条四行**：在等什么 · 等到了立刻做什么 · 起跑前必须满足什么 · 设计细节在哪。

**三条维护纪律**：解掉的条目当场删行（不留「已完成」历史）· 超过复核线（默认 3 天）必须重审或标作废 · 判据正文留在 `TOPIC.md` 或 `plans/`，本页只放指针。

判红方式：专题目录**直接层**出现 `DESIGN_*` 条目（文件或同名目录都算）⇒ 判红（这条后门要真撤掉，否则没人遵守）。判据是可调用的只读检查，不是口号：

```powershell
python -X utf8 -B research.py workspace documents --workspace <工作区> --topic <专题> --check
```

它只判专题目录直接层；该专题 `archive/` 里的历史件不追溯、不判红。

## 6. 归档：就近归档 + 索引，不集中

**位置跟着原件走**：被谁替代，就放在谁的旁边（同级 `archive/`），不放一个全项目的大归档堆。

**每处 archive 一个索引**：一行一条，写「原名 → 归档名 → 字节数 → 哈希 → 被谁替代」。

**命名三件套**：`<原名>_<日期时间>_改前_<为什么改>.md`。三种件分开命名：改前件、被取代件、历史快照。

⚠️ **维护索引是纪律，不是闸** —— 没人写就不会报错。这是已知代价，接受它，但要在动手时先写。

## 7. 口诀：四问决定要不要新开一份文件

1. 这件事**已经有人给过要求**吗？（先查，别重复建）
2. 它**只对一轮有意义**吗？（是 ⇒ 细节层）
3. 它**能由程序重算**吗？（能 ⇒ 不要手工文件）
4. 它**两格都能放**吗？（能 ⇒ 你还没想清边界，先坐下想）

四问都过了才新建。**新建一份文件的成本不是写它，是以后每个读者都要判断要不要读它。**

## 8. 两个反例（结构层面的错，不是笔误）

**反例一：同一件事有三种写法。**
目的写在主文档、写进现状页、又抄进计划文件。三份必然漂，而且**不报错** —— 读者按哪份都像对的，判断却各不相同。修法：只留一份正文，其余全部改指针。

**反例二：归档不写索引，靠文件名猜。**
三个月后没人知道哪个文件是被谁替代的，于是没人敢删、也没人敢用。修法：归档当下就写索引一行；**索引里没有的归档件，等于没归档**。

## 9. 换一个项目怎么复用这套设计

1. **三层**（大纲 / 细节 / 机器账）+ 三问判据（§1）—— 这是骨架，其它都能省。
2. **跨专题资产回上一层**（§4）—— 这条最反直觉，也最容易反复踩。
3. **细节跟着产生它的动作走**（§3）—— 防止细节堆进大纲层。
4. 五格、命名、索引这些是执行细节，可以按项目规模裁剪，但**「一格只有一份正文」不能裁**。
