# 研究项目入口

先整份读[共同规则](<RULES.md>)。写文档前整份读[文档维护](<../kernel/contracts/doc_maintenance.md>)。进入对应工作范围前，显式读相应入口，不能假定宿主已自动加载。
本模板没有比赛结论、历史授权或实际运行状态。具体目标填入[项目说明](<PROJECT.md>)；材料留空不等于检查通过。

## 这份文档是什么

项目唯一的**入口索引**：只写「该做什么」和「东西在哪」。论证、数据与历史都在被指向的分册里，本文件**不复述**。
读者：新开会话的主负责人。时机：开局第一屏，以及每次不确定「这件事该读哪一份」时。

## 里面放什么

- 开局就必须生效、不读就会做错的沟通与行为要求
- 一张「要做什么 → 直接读哪里 → 何时读」的导航表
- 上下文边界：归档里的旧入口不生效、子 agent 怎么派、哪些状态不许写进入口

## 不放什么（放去哪）

| 不写 | 写到哪去 |
|---|---|
| 会漂的量：进度、分数、版本、机器名、端口、费用 | 对应台账正文（本仓库 `project/` 之外） |
| 某条规则的完整正文与其例外 | `RULES.md` 或该线自己的入口 |
| 一次实验的结论、判死理由、读码细节 | 证据文档与负结果台账 |
| 归档目录里的旧版规则 | 不搬；一律以现行入口为准 |

## 一条判据：这条信息该放哪

问：它让我**改行为**、让我**知道事实**、还是让我**动手跑**？
改行为 → `RULES.md`；知道事实 → 资料线；动手跑 → 实验线。三者都不是 ⇒ 它多半属于细节层，不该进这里。

## 和用户说话

先回答用户这次最关心的事。每条回复必须单独可读。默认用户知道目标、结果和方向，不知道 AI 内部文件、代号和工具。
必要的内部名每次出现都补人话解释。用户问什么意思时换说法，不靠堆数据解释。
不对用户观点打总分；直接指出哪条成立、依据是什么。删掉只为防身的话，保留真实条件、数字和不确定性。
实验汇报内部按假设、判据、设置、结果排列；整条回复仍先给答案。
多个实验按对目标的影响排列，用稳定编号识别；同一实验更新先说判词变化。
专题人读报告保留研究八节，由独立 scribe 按完整供料组织。运行状态另存，聊天简短给结论和报告入口。文档失败不阻挡安全停止。

## 上下文边界

归档目录中的旧入口不生效。规则、方案和分析文档按任务选文件，选中的整份读取；历史只在追溯时按编号查。
默认子 agent 是独立新会话，不继承长聊天，不遍历本项目 AGENTS 及全部索引。主会话传递适用约束、指定输入和验收条件；指定源文档仍须全文读。独立审计不能只接负责人结论。
根入口只放必须开局生效的行为与直接导航；分册承载各自正文。实验结论、机器名、版本和当前进度不得写进入口。
